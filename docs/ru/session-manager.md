# Session Manager

Session Manager даёт зарегистрированным приложениям время завершиться, пока дисплей ещё доступен. Он может владеть всем графическим сеансом или подключаться к сеансу, запущенному извне. Он включён по умолчанию и требует Linux pidfd, systemd 250+, logind и пользовательскую шину D-Bus.

## Запуск сеанса {#start-a-session}

::: code-group

```sh [Вход через RSDM]
# Проверка с рабочего стола:
rsdm session status
```

```sh [Из VT]
rsdm session start -- niri-session
```

```sh [Существующий сеанс]
rsdm session attach
rsdm session status
```

:::

Используйте существующую desktop-запись или обёртку композитора. DM автоматически оборачивает исходную команду, поэтому дополнительный start внутри рабочего стола не требуется. Attach сохраняет жизненный цикл внешнего композитора. Первая команда app или finalize также подключается при необходимости. Поддерживается только один координатор на UID.

::: details Режимы запуска
Режим по умолчанию — auto. Для нестандартного сеанса явно выберите managed или external.

```sh
rsdm session start --mode managed -- sway
rsdm session start --mode external --native-unit custom-session.service -- original-wrapper
rsdm session start --mode external --logout-command 'sessionctl logout' -- original-wrapper
```

В последних примерах приведены условные команды и unit, которые нужно заменить своими. Внешние поставщики должны самостоятельно устанавливать готовность и владеть графическим жизненным циклом. Режим managed не может наблюдать нативный unit. Явные нативные команды выхода — буквальный argv, без выражений оболочки.
:::

## Регистрация приложений {#register-applications}

Запускайте первый экземпляр через RSDM:

```sh
rsdm app -- foot
rsdm app --shutdown-timeout 60 --on-timeout cancel -- editor document.txt
rsdm session status
```

Используйте установленные терминал/редактор. Команда app возвращается после запуска. Замените обычные команды в сочетаниях клавиш и автозапуске композитора на rsdm app -- с той же программой и аргументами.

| Параметр | По умолчанию | Действие |
| --- | --- | --- |
| `--shutdown-timeout <seconds>` | 30 | Положительное число секунд ожидания выхода; должно укладываться в ограничения systemd |
| `--on-timeout force\|cancel` | force | Эскалация после тайм-аута или отмена подготовки |
| `--shutdown-method auto\|term\|xsmp` | auto | Выбор метода, SIGTERM или требование допущенного XSMP |
| `--quit-command '<argv>'` | не задано | Документированная команда завершения приложения; требует auto |

Например, если у приложения есть специальная утилита выхода:

```sh
rsdm app --quit-command 'examplectl "quit now"' -- example
```

Замените example и examplectl фактическими командами приложения. Вспомогательный процесс использует записанные окружение и рабочий каталог приложения. Аргументы разбираются буквально, без оболочки.

::: details Как автоматическое завершение выбирает метод
Для управляемых WM и нативного niri auto использует явную команду завершения, допущенный XSMP-клиент, проверенное закрытие окон, затем SIGTERM основному процессу. Force даёт оставшимся принадлежащим приложению процессам до пяти дополнительных секунд на SIGTERM перед SIGKILL. Приложения подготавливаются параллельно. Явный xsmp требует допущенного клиента на момент завершения.

GNOME и Plasma обычно используют собственные проверенные нативные диалоги для приложений auto. Явные политики term/quit-command выполняются до делегирования. Auto с cancel отклоняется при доступном проверенном нативном управлении, поскольку RSDM не может обеспечить отмену внутри нативных диалогов.

Охватываются только зарегистрированные invocation и проверенные потомки/scope. Запускатель, перенаправляющий запрос в посторонний существующий экземпляр, не может перенять его. Ни один метод не гарантирует сохранение данных приложением. См. [детали бэкендов](reference/session-backends.md) и [внутреннее устройство владения](reference/session-lifecycle.md#registering-applications).
:::

## Готовность {#readiness}

Композитор должен опубликовать действующее окружение дисплея до запуска служб, зависящих от target.

```sh
rsdm session finalize
rsdm session finalize MY_VARIABLE
```

Официальный niri-session обычно обрабатывает готовность сам. Bare WM могут выполнять finalize из конфигурации запуска. Готовность управляемого сеанса может определяться автоматически; при тайм-ауте targets остаются неактивными до последующего finalize. Повторный finalize обновляет окружение.

См. примеры настройки [niri](compositors/niri.md), [Hyprland](compositors/hyprland.md) и [Sway](compositors/sway.md).

::: details Окружение и графические targets
RSDM сохраняет PATH, LANG, `XDG_RUNTIME_DIR`, проверенную идентичность сеанса и существующие метаданные seat/VT. Он захватывает актуальные `WAYLAND_DISPLAY`, DISPLAY, XAUTHORITY и поддерживаемые endpoints композиторов (`NIRI_SOCKET`, `SWAYSOCK`, `HYPRLAND_INSTANCE_SIGNATURE`, `WAYFIRE_SOCKET`). Используйте `session_manager.extra_env` или имена в finalize для дополнительных переменных.

Управляемый сеанс удерживает `graphical-session.target` и xdg-desktop-autostart.target. Нативные поставщики владеют собственными targets. Подключённые сеансы используют частное окружение приложений и не изменяют глобальное владение targets. См. [внутреннее устройство готовности](reference/session-lifecycle.md#readiness-and-recovery).
:::

## Выход и питание {#logout-and-power}

Сохраните важную работу, затем используйте эти команды или назначьте их в композиторе:

```sh
rsdm session stop
rsdm power reboot
rsdm power poweroff
```

Чтобы запросить отмену во время подготовки приложений, выполните rsdm session cancel из другого терминала. Она доступна до необратимого начала демонтажа; уже закрытые приложения не восстанавливаются.

Для подключённого сеанса без проверенного нативного выхода stop подготавливает зарегистрированные приложения и оставляет исходный рабочий стол работающим. После этого используйте обычное действие выхода рабочего стола. Нативные GNOME и Plasma могут делегировать собственным диалогам. Запросы питания остаются под политикой logind/polkit или нативной политикой.

::: warning
Прямой выход из композитора, сбой или потеря питания могут убрать дисплей до завершения сохранения приложениями. Force — политика тайм-аута по умолчанию.
:::

::: details Интерактивный монитор питания
В поддерживаемом терминале команды power сообщают этапы, методы приложений и длительность ожиданий, jobs systemd и ингибиторы. Полоса этапов представляет наблюдаемые стадии, а не оценочный процент. Ctrl+C прекращает наблюдение; отправленный запрос может продолжиться. Терминал в графическом сеансе исчезает при его завершении. Перенаправленный вывод использует разовые отчёты. Suspend и hibernate не подготавливают выход.
:::

## Статус и результаты {#status-and-outcomes}

Выполните rsdm session status, чтобы проверить работающий координатор без его запуска.

| Область | Значение |
| --- | --- |
| inactive | Нет работающего координатора |
| disabled | Координация отключена в конфигурации |
| full | Координатор владеет проверенным графическим жизненным циклом |
| partial | Подключённый сеанс или необходимое управление жизненным циклом недоступно/неизвестно |

Фаза показывает запуск, работу, подготовку приложений или демонтаж. Возможности содержат причину для состояний available, unavailable, not-applicable и unknown.

| Результат stop | Значение |
| --- | --- |
| completed | Управляемый выход завершён |
| prepared | Приложения подготовлены; исходный рабочий стол остаётся |
| delegated | Нативный рабочий стол принял запрос; он может ещё запросить подтверждение |
| cancelled / failed / unknown | Операция отменена, не удалась или результат невозможно установить |

Результаты подготовки приложений включают clean, forced, cancelled и unknown. Clean означает отсутствие зарегистрированной эскалации, а не гарантию сохранения данных. Проверьте фактический результат и нативный диалог, прежде чем считать выход завершённым.

## Отключение координации {#disable-coordination}

::: code-group

```toml [TOML]
[session_manager]
enabled = false
```

```nix [NixOS]
services.rsdm.sessionManager = false;
```

:::

Проверенное изменение конфигурации во время работы отключает координацию, оставляя приложения, рабочий стол и окружение работающими. Для повторного включения после прекращения поколения нужен новый вход. DM, Lock и PAM продолжают работать независимо.

См. [конфигурацию](configuration.md#session-manager), [устранение неполадок](troubleshooting.md), [справочник бэкендов](reference/session-backends.md) и [внутреннее устройство жизненного цикла](reference/session-lifecycle.md).
