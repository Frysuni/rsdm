# Реализация Session Manager и graceful shutdown на Tokio

## 1. Архитектура и runtime

Полностью перенести асинхронную работу проекта на Tokio, выделить Session Manager в самостоятельный crate и обеспечить его работу без DM и в сессиях, запущенных другим способом. Сохранить проверку владельцев процессов, отмену подготовки, XSMP и делегирование завершения GNOME/Plasma.

- Создать `rsdm-session-manager`. Перенести туда координатор, регистрацию приложений, systemd user units, состояние и recovery, управление завершением приложений, XSMP и Wayland backends. Crate не зависит от `rsdm-infra`, DM, Greeter или Lock.
- Вынести уже используемые несколькими компонентами Linux process handles, монотонные часы и низкоуровневый logind transport в небольшой `rsdm-system`. Он не содержит политик Session Manager. PAM и аутентификация остаются в DM; маршрутизация пользовательских действий — на уровне CLI и Lock.
- Удалить прямые зависимости и обращения к `async-io`, `async-channel`, `futures-lite`, а также `zbus::blocking`. Использовать Tokio для каналов, сокетов, таймеров, subprocess, сигналов и задач. Перевести существующие тестовые fixtures.
- Зафиксировать Tokio 1.53.2 в lockfile; сохранить MSRV проекта 1.88. Для zbus 5.14 оставить `default-features = false`, включить `tokio`, убрать `async-io` и `blocking-api`. Такой backend предусмотрен самим [zbus](https://docs.rs/crate/zbus/5.14.0/source/Cargo.toml).
- Координатор сделать одним последовательным actor: `select!` обрабатывает запросы, изменения конфигурации, события backend, logind и deadlines. Короткие операции выполняются с ограниченной конкурентностью; ожидание выхода приложения не удерживает слот отправки запросов другим приложениям.
- Синхронные файловые операции изолировать через `spawn_blocking`. Отмена задач не должна считаться отменой уже выполненного внешнего действия.
- libSM/libICE оставить на одном выделенном потоке с Tokio current-thread runtime. Ожидание дескрипторов перевести на `AsyncFd`; синхронный FFI не блокирует координатор. Отключение прерывает ICE-соединения и завершает worker без неограниченного `join`.

**PAM и fork:** не добавлять `#[tokio::main]` ко всему CLI. Greeter до `fork` не использует Tokio; обращения к logind из Greeter выполняются через отдельный helper с `exec`. Runtime PAM-владельца создаётся после fork, а session-exec — в свежем процессе. Это необходимо из-за [ограничений Tokio после fork](https://docs.rs/tokio/latest/tokio/runtime/index.html).

## 2. `enabled`, самостоятельный запуск и `partial`

Существующий `[session_manager].enabled` становится обязательным условием для **всех** функций Session Manager, включая внутренние hooks и recovery. Значение по умолчанию сохраняется: `true`.

| Условие | Статус | Поведение |
|---|---|---|
| `enabled = false` | `disabled` | Функции Session Manager отключены |
| Включён, координатор ещё не запущен | `inactive` | Чтение статуса ничего не запускает |
| Session Manager запустил сеанс и располагает необходимым lifecycle-контролем | `full` | Подготовка приложений и завершение принадлежащей ему сессии |
| Подключён к внешней сессии либо утратил необходимый lifecycle-контроль | `partial` | Доступные функции работают; ограничения перечислены в статусе |

Выключенный DM сам по себе не вызывает `partial`. Сеанс, запущенный вручную через `rsdm session start`, может иметь полноценный Session Manager.

**Самостоятельный запуск:**

- Добавить `rsdm session attach`: подключить менеджер к текущей графической сессии без запуска или перезапуска WM.
- При первом `rsdm app` или `rsdm session finalize` автоматически запускать координатор и выполнять attach, если менеджер включён и подходящего координатора нет.
- Использовать отдельный transient user service с внутренней командой `session serve`. Его запуск и остановка не управляют compositor unit.
- Сохранить ограничение одного активного координатора на UID. Параллельные запросы используют существующий lease; запрос из другой графической сессии получает явную ошибку.
- Generation получать через проверенный handshake с координатором. Переменные окружения служат подсказками; одного `RSDM_SESSION_GENERATION` недостаточно для подтверждения принадлежности.
- Проверять UID, идентичность вызывающего процесса и его logind-сессию. Для приложений, запущенных через user manager, разрешать подтверждение по зарегистрированной cgroup и актуальному InvocationID.

**В режиме `partial`:**

- Работают запуск и регистрация приложений, индивидуальные политики, quit-command, наблюдение cgroup, доступный XSMP, безопасное закрытие окон, отмена подготовки и обработка logind.
- App units не требуют активного `graphical-session.target` и не привязываются к чужому anchor. Окружение хранится для текущего поколения и передаётся запускаемым приложениям.
- Менеджер не останавливает внешний WM, его units, общие graphical targets или чужую PAM-сессию; не меняет фокус, раскладку и конфигурацию WM.
- Уже работающие сторонние приложения не становятся управляемыми автоматически. Статус явно показывает, что гарантии завершения распространяются на зарегистрированные приложения.
- Собственный XSMP endpoint передаётся новым управляемым приложениям без замены глобального XSMP endpoint внешнего desktop.
- `session stop` использует штатное делегирование GNOME/Plasma, когда оно доступно. В остальных случаях завершает подготовку зарегистрированных приложений, возвращает `prepared` и оставляет WM работающим.
- Reboot/poweroff после подготовки передаются logind. Команда logout не подменяется принудительным завершением logind-сессии.

**При `enabled = false`:**

- `rsdm app` и `session start` выполняют исходную команду обычным запуском, без регистрации, units и shutdown-политик Session Manager.
- `finalize`, stop hooks и cleanup ничего не меняют. `attach`, `stop`, `cancel` возвращают результат `disabled`.
- Не запускаются координатор, XSMP, Wayland connections, подписки и inhibitor Session Manager.
- Обычные действия питания DM и Lock продолжают работать через logind.

**Горячее отключение:**

- Слой загрузки конфигурации следит за файлом и его заменой через rename; передаёт актуальную конфигурацию координатору через Tokio `watch`. Crate Session Manager не импортирует загрузчик из `rsdm-infra`.
- При переходе в `false` закрыть admission, отменить подготовку, запретить новые внешние действия, записать состояние отключения и завершить coordinator/backend tasks.
- Остановить только инфраструктуру самого менеджера. Не останавливать работающие приложения, WM или anchor с живыми зависимостями; не очищать нужное им display-окружение.
- Отделить время жизни координатора от обычного launcher, который удерживает запущенный сеанс и позволяет DM закрыть PAM после фактического выхода WM.
- Уже созданные lifecycle-зависимости остаются пассивными до завершения сеанса. План не рассчитывает изменить их через `SetUnitProperties`: в поддерживаемом systemd такие настройки transient unit задаются при создании. [Исходный код systemd](https://raw.githubusercontent.com/systemd/systemd/v250/src/core/dbus-unit.c).
- Уже принятую ОС или compositor команду невозможно отозвать гарантированно. Отключение запрещает следующие действия; неподтверждённый результат отражается как `unknown`.
- Возврат в `true` разрешает новый attach при следующем явном обращении. Старые hooks не возобновляют остановку прежнего поколения.

## 3. Graceful shutdown и Wayland backends

Для `auto` использовать порядок: **quit-command → подтверждённый XSMP → безопасный window-close → существующий TERM fallback**. Явные `term` и `xsmp` сохраняют свою семантику; отсутствие явно выбранного XSMP не маскируется успешным завершением.

**Общие правила:**

- Принадлежность проверять по generation, актуальному InvocationID, cgroup и устойчивой идентичности процесса через pidfd/start time. `app_id`, title, WM_CLASS и заявленный XWayland PID сами по себе недостаточны.
- Для приложения отправлять один window-close на один InvocationID. Выбирать первое адресуемое окно по устойчивому идентификатору, предпочтительно без родительского окна.
- После отправки не закрывать другие окна приложения и появившийся диалог сохранения. После отмены новый logout не повторяет close для того же InvocationID.
- До внешнего действия сохранять намерение dispatch. При потере ответа или рестарте координатора считать действие потенциально выполненным и не повторять его.
- Отправка команды, исчезновение окна и XSMP SaveDone не доказывают завершение приложения. Завершение подтверждается состоянием unit и отсутствием процессов в его cgroup.
- Fallback разрешён, если доказано, что предыдущий способ ничего не отправил. Неопределённый результат ведёт к наблюдению и timeout-политике.
- Отправлять запросы всем приложениям без ожидания выхода предыдущей пачки. Ограничить число одновременно выполняемых IPC/DBus операций четырьмя.
- Обычный общий deadline: момент начала остановки + максимальный app timeout, либо 30 секунд при отсутствии приложений, + существующий запас 90 секунд. Все операции и escalation укладываются в этот бюджет; replay его не продлевает. Logind может сократить бюджет.
- Сохранить `force`/`cancel`, возможность отмены до teardown и TERM/KILL escalation только для проверенной текущей invocation.

**Backend capability определяется в runtime:**

| Backend | Реализация и условия закрытия |
|---|---|
| Niri | Прямой IPC: Windows, события, адресный CloseWindow. Проверять PID и идентичность compositor instance. Поддержать bare niri и niri-session |
| Hyprland | Прямые command/event sockets. Использовать устойчивый window identity и адресное закрытие с проверкой актуального объекта; address-only путь отключать, если нельзя исключить повторное использование адреса |
| Sway | Бинарный IPC, GET_TREE, nodes/floating_nodes, события и `[con_id=…] kill`; подтверждать актуальность container и владельца |
| Wayfire | Length-prefixed JSON IPC: list-views, view-info, close-view. Проверять доступность plugins, owner и устойчивость view identity; при недостаточных гарантиях оставить discovery и fallback |
| KWin standalone | `org_kde_plasma_window_management`: проверенный PID, parent и close на живом protocol handle |
| Generic Wayland | Обнаруживать ext foreign-toplevel list и wlr foreign-toplevel management. Закрывать только при дополнительном доказательстве владельца и принадлежности конкретного handle |
| Labwc | Обнаруживать доступные протоколы; отсутствие безопасного ownership/close API отражать как ограничение |
| River | Не занимать исключительную роль window manager. Использовать только независимый доступный API с достаточными гарантиями; иначе fallback |
| GNOME/Plasma | Сохранить штатные logout/reboot/shutdown API и диалоги desktop; не запускать параллельное массовое закрытие его приложений |

Generic-протоколы сами по себе не дают достаточной связи handle с PID/cgroup, поэтому объединение окон по title или `app_id` запрещено. [ext protocol](https://github.com/wayland-mirror/wayland-protocols/blob/main/staging/ext-foreign-toplevel-list/ext-foreign-toplevel-list-v1.xml), [wlr protocol](https://github.com/swaywm/wlr-protocols/blob/master/unstable/wlr-foreign-toplevel-management-unstable-v1.xml).

IPC реализовать на Rust без обязательных `hyprctl`, `swaymsg`, `niri msg` и `jq`. Endpoint-переменные получать при start/attach/finalize, проверять и хранить отдельно для каждого поколения. Не редактировать конфигурацию WM ради включения backend.

## 4. Интерфейсы, состояние и диагностика

- Публичные функции нового crate сделать асинхронными. Передавать им конфигурацию явно; работающий координатор получает её обновления через `watch`. Внутри библиотеки не создавать вложенные runtimes и не выполнять `block_on`.
- Сохранить существующий D-Bus `org.rsdm.Session1` и wire-форматы Status/Stop. Добавить авторизованный Attach и отдельный StatusDetails.
- StatusDetails содержит `enabled`, состояние `inactive/full/partial/disabled`, существующую phase, provider, доступные capabilities, причины ограничений и последние результаты подготовки приложений.
- CLI показывает `partial` и конкретные причины, например отсутствие владения compositor lifecycle. Необязательный backend, не предусмотренный выбранным provider, отображается отдельно и сам по себе не означает потерю lifecycle-контроля.
- Добавить результаты `prepared` и `disabled` без изменения структуры StopOutcome. Для завершения приложений различать `clean`, `forced`, `cancelled`, `unknown`; `clean` означает отсутствие escalation, а не гарантию сохранения данных.
- Хранить shutdown transaction, выбранный метод, dispatch state и факт отправки close вместе с InvocationID. Отмена сбрасывает текущую подготовку, но сохраняет запрет повторного close.
- Новые поля старых runtime-записей получают безопасные defaults. Старое `quit_started=true` трактуется как возможное выполненное действие.
- Новый CLI при отсутствии StatusDetails у старого сервера использует прежний Status. Чтение статуса не активирует manager.
- Обновить root `rsdm.toml`, CLI help, документацию и Nix-описания независимости `dm.enable` и `sessionManager`. XSMP feature и проверку SM/ICE перенести в новый crate; PAM dependency там отсутствует.

## 5. Порядок реализации и проверки

Выполнять этапы отдельными проверенными коммитами:

1. Выделить Session Manager и общие системные операции; сохранить текущую функциональность.
2. Перевести весь существующий async-код и fixtures на Tokio, устранить нарушения fork/runtime lifecycle.
3. Реализовать полный контракт `enabled`, горячее отключение и независимое время жизни launcher.
4. Добавить attach, автоматический запуск и `partial`.
5. Реализовать устойчивую shutdown transaction, однократный dispatch и конкурентное наблюдение приложений.
6. Добавить Niri, Hyprland и Sway, затем расширенные backends и безопасные fallback.
7. Завершить диагностику, совместимость, документацию и интеграционные проверки.

**Обязательные сценарии:**

- `enabled=false` до запуска: нет coordinator, XSMP, inhibitors, backend connections, app units и побочных эффектов hooks; исходные приложения запускаются.
- Отключение во время idle, запуска приложения, dispatch, диалога сохранения, наблюдения выхода и recovery: новых shutdown-действий нет; PAM не закрывается преждевременно.
- DM выключен: ручной start даёт полноценное управление; attach к внешнему WM даёт `partial`.
- Внешний сеанс с неактивным graphical target: `app` и `finalize` запускают менеджер; `status` этого не делает; non-native stop возвращает `prepared`, WM остаётся жив.
- Нет generation в окружении, generation устарел, UID/session не совпадают, одновременный autostart и занятый lease.
- Более четырёх приложений, несколько окон, дочерние процессы после выхода main PID, отсутствие PID, повторное использование PID/unit/window identity.
- Потерянный ответ, обрыв IPC, неполный frame, зависший peer, рестарт coordinator, отмена и повторный logout: close не дублируется.
- Force/cancel, сокращение logind deadline, отмена внешнего shutdown и native desktop dialogs.
- Отсутствующий или несовместимый backend приводит к заявленному ограничению и разрешённому fallback.

**Команды проверки при реализации:**

```text
nix develop -c cargo test --workspace --locked
nix develop -c cargo test -p rsdm-session-manager --no-default-features --locked
nix develop -c cargo test -p rsdm --no-default-features --locked
nix develop -c cargo check --workspace --all-targets --locked
nix develop -c cargo tree --workspace -e features -i async-io
nix flake check --all-systems --no-build
```

Последняя Cargo-проверка должна подтвердить отсутствие активной зависимости `async-io`. Дополнительно выполнить существующие Nix VM checks для session lifecycle, native Niri/desktop handoff, power, Lock и DM; расширить их случаями disabled/attach/partial. Сохранить проверку Rust 1.88 в CI.

Реальные compositor backends проверить в изолированных графических сессиях, включая браузер, GTK/Qt приложение с несохранёнными изменениями, OBS, Mumble, Waybar, Flatpak и XWayland. Поддержку объявлять только после проверки соответствующего транспорта и ownership.

Новые модули держать преимущественно до 300 строк; превышения 400 строк и функции более 50 строк обосновывать при self-review. Не запускать fmt/Clippy/actionlint и не добавлять их в CI. Каждый завершённый этап коммитить после проверок; версию и push не выполнять без отдельного разрешения.

При подготовке плана выполнено чтение и поиск по коду, конфигурации и upstream-документации. Файлы не изменены; сборка и тесты ещё не запускались. Ограничения внешних сессий и backend без доказуемого ownership являются частью предусмотренного `partial`/capability-поведения.
